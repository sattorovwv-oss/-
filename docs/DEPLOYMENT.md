# Развёртывание и рабочая приёмка

## Что потребуется

- Linux VPS с Docker Engine и Compose plugin; начальная рекомендация: 2 vCPU, 2 ГБ RAM, постоянный SSD. Доступ по SSH.
- Домен и A-запись на IP VPS; AAAA добавляется только при рабочем IPv6. Открыты входящие TCP 80/443, UDP 443 необязателен. Порт 8000 наружу не публикуется.
- Токен @BotFather и Telegram ID уполномоченных сотрудников. Предыдущий polling/webhook для этого бота должен быть остановлен; webhook удаляется осознанно оператором перед первым polling-запуском.
- Место для внешних резервных копий и ответственный за восстановление.

GitHub Pages не является сервером для этого приложения. Репозиторий можно хранить в GitHub; секреты и персональные данные хранятся только на сервере.

## Docker Compose

Клонируйте проект на VPS. Создайте `.env` из примера и ограничьте его права `chmod 600 .env`. Установите:

- `APP_ENV=production`, `WEB_ONLY=0`.
- `DOMAIN=ваш-домен` (только hostname) и `PUBLIC_URL=https://ваш-домен`.
- `BOT_TOKEN` — настоящий токен, введённый на сервере, не в чате или Git.
- `OWNER_PASSWORD`, `CHINA_PASSWORD`, `TAJIK_PASSWORD` — разные первоначальные пароли по 12–128 символов. Общедоступные примеры из переписки использовать нельзя.
- `OWNER_TELEGRAM_IDS`, `CHINA_TELEGRAM_IDS`, `TAJIK_TELEGRAM_IDS` — нужные числовые ID, один ID не назначается двум ролям.

```sh
docker compose config --quiet
docker compose up -d --build
docker compose ps
docker compose logs --tail=50 app
```

`config --quiet` проверяет структуру, не печатая содержимое env. Обычный `docker compose config` может раскрыть секреты, его вывод нельзя публиковать. Caddy получает/обновляет сертификат HTTPS. Начальные логины: `owner`, `china`, `tajik`; пароли — введённые владельцем при развёртывании. В `.env` нет встроенных рабочих паролей.

Если сеть использует собственный доверенный CA для HTTPS-прокси, Docker build принимает необязательный BuildKit secret `custom_ca`: `docker build --secret id=custom_ca,src=/путь/к/доверенному-ca.pem -t tuman-kargo .`. Проверка TLS остаётся включённой; CA не попадает в образ. В обычной сети этот параметр не нужен. Для прокси во время работы контейнера также требуется отдельно настроить стандартные переменные прокси и смонтировать доверенный CA только для чтения.

При последующих запусках начальные пароли не перезаписывают реквизиты в БД. Смена логина не создаёт заново старый аккаунт. После первоначальной настройки пароли bootstrap можно удалить из `.env` и пересоздать контейнер: они уже сохранены в БД как хеши. Не удаляйте том `tuman_data`.

Создание дополнительных администраторов и аварийный сброс пароля:

```sh
docker compose exec app python -m tuman.cli create-admin --role china --login china_operator2
docker compose exec app python -m tuman.cli bind-telegram --login china_operator2 --id YOUR_NUMERIC_ID
docker compose exec app python -m tuman.cli reset-password --login owner
```

Не запускайте несколько экземпляров/worker-ов, не масштабируйте app: используется один Telegram polling и SQLite. Файловая блокировка защищает общую БД, но не разные серверы с одним токеном.

В Compose заголовкам proxy доверяет только не опубликованный наружу сервис app за Caddy; Caddy формирует адрес клиента. При другом развёртывании `FORWARDED_ALLOW_IPS` должен содержать только адреса доверенного reverse proxy. Не публикуйте порт 8000 с доверенным `*`: это позволяет подменять адрес в списке сессий и обходить ограничения по IP.

## Бэкапы и восстановление

```sh
docker compose exec app python -m tuman.cli backup
docker compose exec app python -m tuman.cli check-db
```

Копии лежат в `/app/var/backups` внутри постоянного тома, 28 последних. Внешний планировщик должен копировать завершённые `.db`-бэкапы на другой носитель с ограниченными правами. Это SQLite Backup API; копировать живой основной `.db` отдельно от WAL нельзя.

Восстановление сначала проверьте на отдельной машине без Telegram polling. Остановите app, сохраните повреждённую БД вместе с WAL/SHM для диагностики, выберите проверенный бэкап, восстановите его в томе с владельцем UID/GID 10001. Не смешивайте восстановленную БД со старыми WAL/SHM. Проверьте `PRAGMA integrity_check`/CLI, количества и несколько известных посылок. Только после этого запускайте один app. Повторная отправка некоторых сообщений из старого бэкапа возможна; оператор должен учесть её.

## Контроль перед передачей заказчику

1. Проверить HTTPS на реальном домене и доступ с устройств обоих складов, верный PUBLIC_URL, вход/выход/смену пароля/отзыв сеансов.
2. Назначить реальные Telegram ID. Проверить /start, оба языка, /panel с отдельными правами и /website клиента. Клиент не должен получить права склада через регистрацию или подмену запроса.
3. Настроить каждый сканер: режим USB/Bluetooth HID keyboard, суффикс Enter, корректная раскладка. Протестировать реальные форматы штрихкодов, буквенные и цифровые коды, 20 быстрых сканов, повторы, разрыв связи и перезагрузку страницы с очередью.
4. Выполнить полный путь одной посылки: заявка, проверка владельца, Китай, отправка, Таджикистан, оплата, выдача. Скан в Китае после Таджикистана не понижает статус. Скан раньше заявки тоже работает.
5. Получить реальные уведомления. Проверить временное отсутствие связи и блокировку бота клиентом. Время до пяти секунд измерять на рабочей инфраструктуре, отдельно учитывать Telegram rate limits.
6. Проверить ручной вес, денежное округление, неизменность старых цен после смены тарифа, Excel, поддержку и рассылку сначала на согласованной небольшой группе.
7. Проверить restart контейнера, наличие данных, бэкап и практическое восстановление на отдельной базе. Настроить внешние копии, мониторинг доступности, ошибки приложения и заполнение диска.
8. Подтвердить складские правила проверки владельца/получателя и вычитать таджикские тексты.

Не обещайте отсутствие любых ошибок на основании автотестов. Пока не выполнены проверки с настоящим Telegram, доменом и сканерами, рабочая приёмка не завершена.
