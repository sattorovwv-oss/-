# Вход клиентов через Google

Вход Google дополняет логин/пароль и вход из Telegram. Новый пользователь
получает только роль customer. Существующий клиент сначала входит привычным
способом, открывает «Ҳисоб ва сессияҳо» и нажимает «Подключить Google».
Посылки, заявки и Telegram остаются в том же кабинете. Если Google уже относится
к другому кабинету, привязка отклоняется; автоматического объединения по email нет.

## Настройки Google

Создайте OAuth client типа **Web application** в Google Auth Platform.
Для рабочего домена зарегистрируйте точный Authorized redirect URI:

    https://tumancargo.cfd/auth/google/callback

При другом домене используйте PUBLIC_URL + /auth/google/callback. Адрес берётся
из конфигурации сервера, а не из заголовка Host. JavaScript SDK не используется;
Client Secret браузеру не передаётся.

Нужны Client ID и Client Secret. В режиме **Testing** аккаунты для проверки
нужно добавить в **Audience → Test users**. Для общего доступа переведите
приложение в Production, выполнив требования консоли Google к приложению.

## Обновление действующего VPS

Команды выполняются в SSH на Ubuntu, не в локальном PowerShell. Сначала
сделайте штатную резервную копию работающей базы:

```sh
docker compose --env-file /opt/tuman-kargo/.env -f /opt/tuman-kargo/compose.yaml exec app python -m tuman.cli backup
git -C /opt/tuman-kargo pull --ff-only origin main
```

Если Git сообщает о локальных изменениях или конфликте, сохраните их и решите
конфликт перед продолжением. Не заменяйте рабочую базу пустой.

Введите публичный Client ID через аргумент, а Client Secret — в скрытом запросе:

```sh
python3 /opt/tuman-kargo/scripts/configure_google.py --client-id YOUR_CLIENT_ID.apps.googleusercontent.com
```

Скрипт меняет только GOOGLE_CLIENT_ID и GOOGLE_CLIENT_SECRET. Предыдущий .env
сохраняется в закрытую резервную копию, новый файл заменяется атомарно с правами
0600. BOT_TOKEN, пароли и Telegram ID остаются прежними. Секрет не печатается,
не передаётся в аргументах командной строки и не записывается в историю оболочки.

Client Secret — отдельное значение из настроек OAuth-клиента; он часто
начинается с GOCSPX-. В скрытый запрос вставляйте только это значение.
Скрипт сообщает конкретную причину отказа (например, пустой секрет, Client ID
вместо секрета, формат, доступ к файлу или UTF-8), не печатая секрет и содержимое
.env. Кавычки вокруг скопированного значения и парные служебные обёртки
bracketed paste Windows SSH удаляются перед проверкой.

После успешной настройки:

```sh
docker compose --env-file /opt/tuman-kargo/.env -f /opt/tuman-kargo/compose.yaml config --quiet
docker compose --env-file /opt/tuman-kargo/.env -f /opt/tuman-kargo/compose.yaml up -d --build app
docker compose --env-file /opt/tuman-kargo/.env -f /opt/tuman-kargo/compose.yaml ps
```

Добавление таблиц выполняется при запуске приложения. Существующие аккаунты,
сессии, посылки, привязки Telegram и настройки сохраняются. На время пересоздания
app возможен короткий перерыв; Caddy продолжает работать. Один работающий app
сохраняет единственный Telegram polling.

## Пользовательские сценарии

- Новый клиент нажимает «Продолжить с Google» на /login или /register, выбирает
  Google-аккаунт и попадает в кабинет. Отдельный пароль при этом не нужен.
- Повторный вход с тем же Google открывает тот же кабинет, в том числе после
  изменения Google email.
- Существующий клиент подключает Google из собственного профиля после входа
  по паролю или Telegram. Кнопка на странице /login не объединяет кабинеты.
- Для аккаунта, созданного через Google, можно установить дополнительный пароль
  и удобный логин в профиле в течение 10 минут после Google-входа. В дальнейшем
  изменение реквизитов требует текущий пароль, как для остальных аккаунтов.
- Привязка Telegram и уведомления работают тем же способом, что при обычной
  регистрации: /website и подтверждение привязки в своём кабинете.
- Для сотрудников Google-вход не назначает и не подтверждает служебные права.

## Проверки и границы

Используется server-side OAuth authorization-code flow: одноразовый state
привязан к текущему сеансу браузера, срок действия 10 минут, PKCE S256.
Обмен кода аутентифицирован Client Secret и выполняется с проверкой TLS на
фиксированном HTTPS endpoint Google, без переходов по редиректам. Идентичность
получается из аутентифицированного HTTPS UserInfo и связывается по sub.
ID token не используется как источник идентичности; браузерный профиль не
принимается. Access/refresh tokens в базе и браузере не сохраняются.

Сеанс после входа или привязки ротируется. Отключённые аккаунты и служебные
роли через Google не входят. Отмена, сетевые ошибки, истёкший state, смена
браузера и повтор callback не создают аккаунты и не раскрывают секреты.

Локальные проверки:

```sh
python -m pytest -q
python -m tests.browser_flow
python -m tests.browser_google
```

Браузер Google в тесте имитируется; реальный server-side callback, cookie,
CSRF и PKCE выполняются в Chromium с отдельной временной базой. Тестовый
адаптер находится только в tests/browser_app.py и исключён из Docker-образа.
Проверки с настоящим Google-аккаунтом после настройки клиента и секрета на VPS
обязательны: локальные проверки не подтверждают доступность провайдера и
настройки Google Cloud.
